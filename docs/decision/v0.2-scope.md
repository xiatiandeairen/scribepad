# Decision: v0.2 Scope Convergence

> **Date**: 2026-05-02
> **Status**: locked
> **Context**: v0.2 sprint 启动前,22 轮探索性 Q/A 后用户拉回收敛。本文档记录"为什么选这套 + 为什么 defer 那一堆",防止后续 sprint 重新发明轮子。

## 决策

**v0.2 范围严格限定为 7 个功能**:
1. 浏览器渲染 markdown
2. 选区 → popover → 输入修改意图
3. AI 改写 + diff modal + accept / cancel
4. sidebar 批注列表 + 锚点对齐
5. sidecar JSON 持久化
6. **拍板**:段 / 选区标"已决定" → state=decided + 绿徽章 + 微变色
7. **防漂移**:AI 改写时 prompt 自动 exclude state=decided 段

前 5 项 = 重建 MVP 核心(在新 Vite+TS 底座上);后 2 项 = v0.2 wedge。

## 上下文 — 我们是怎么走到这的

foundation sprint(20260501-234711-912)删掉了 v0.1 MVP 代码,留下空骨架。原 roadmap v0.2 = "活文档(段落级 4 态状态机 + 防漂移)"。

v0.2 sprint 启动前,用户对该 scope 表达不满 — 不想做"把 v0.1 重建 + 加状态机"这样累赘的版本。要求"从零重新设计,只借鉴经验"。22 轮 Q/A 探索新的产品方向。

22Q 浮现的产品形态(候选,**未采用**):
- 单文件 plan auditor — 自动 audit pass + 5 sidebar component + 状态机
- 信息密集首屏(摘要 + 自动高亮 + 5 类 aggregator + 时间轴)
- inline 编辑 + 版本归档 + AI overwrite diff merge
- 灵活粒度(selection / 段 / 用户框定块)
- 评论 / 反驳 状态机(后被合并入 draft mark 的 note 字段)

最后 2 轮用户拉回:
> "我验证了 MVP 的价值,我现在需要你收敛下来,找出价值点,定义 v0.2 要做的功能集合,验证完再做下一步"
> "0.2 拍板+防漂移+评论交互修改,这一版本的价值是可以足够支撑日常修改审阅日常,更新文档"

## 为什么选这 7 个,不选别的

### 选这 7 个的理由

| 功能 | 为什么必须 |
|------|---------|
| 1-5(重建 MVP 核心) | foundation sprint 删了 MVP,v0.2 没这 5 项就不能日常用 |
| 6 拍板 | 22Q 发现这是 scribepad 区别于"通用 markdown viewer"的最小 wedge — 用户痛点是"AI 反复改飞,决定丢失",拍板 + 防漂移直接解 |
| 7 防漂移 | 拍板没有"AI 改写时跳过 decided"配套就是装饰品 |

### Defer 列表(22Q 中讨论但未进 v0.2)

| 候选功能 | Defer 理由 | 触发条件(进 v0.3+) |
|---------|---------|-----------|
| AI auto-audit(找 TBD/风险/范围) | 工程量中,价值假设未验证;AI 抽取可能不准 | dogfood 中作者多次主动想"全文扫一遍弱点"则进 v0.3 |
| AI summary 头部 | nice-to-have,不改变核心 loop | dogfood 中"读不进去 / 找不到重点"频次高则进 |
| 5 component sidebar(待审/已决定/风险/范围/行动项) | 工程量大,过度结构化,v0.2 阶段简单批注列表够用 | 单一批注列表不够用、用户需要 aggregation 视图时进 |
| inline 双击编辑 markdown | 复杂(contenteditable / 编辑器集成),对核心 loop 边际 | popover-instruction 不够、用户大量需要"自己改原文"时进 |
| 版本归档 / AI overwrite diff merge | 工程量大,假设 AI 在 Cursor 频繁覆盖文件 | dogfood 中 AI overwrite 实际造成痛点(数据丢失 / 冲突)时进 |
| 多 agent 协议(MCP / cursor adapter / aider) | 实际 dogfood 不需要 second-opinion(用户在 Q11 否决) | 长期可作部署属性,但运行时多 agent 是死路,不再考虑 |
| 4 场景模板差异化(plan/design/research/analysis) | v1 只深做 plan,其他 v2+ | plan 命题验证后再延伸 |
| 反驳 / counter-notes(独立 sidebar 评论层) | 与 我改 / 拍板 功能重叠,已合并入 draft mark 的 note 字段(v0.3+ 可加 note 字段) | 实际 dogfood 中"想留下疑问但不改"频次高时进 |
| 自动跨段 / 跨格式 anchor 重建 | v0.1 已实现 mdast offset 锚点,v0.2 复用 | — |
| Block 概念(用户框定的多段块) | selection range 单一类型已够覆盖 | dogfood 中频繁需要把多段 group 时进 |
| 灵活粒度键盘快捷选(j/k/v/V) | 鼠标选区已够,键盘加速边际 | 用户高频审计、键盘党需求出现时进 |

## 验证标准(roadmap 沿用)

- 作者写 ≥1 份真实 plan(scribepad 项目自身的下版 plan 即可)
- 使用"拍板" ≥10 次
- self-report"AI 反复改飞 / 决定丢失"焦虑显著下降

**通过 → v0.3 从 defer 列表选 1 个候选验证**(选哪个由 dogfood 反馈定,不预设)
**不通过 → 命题被否,停或重做**

## 关键约束(不可违反)

1. **不引入新依赖**:除非工程上极致必要(diff 库或可),否则用现有 stack(Vite + React + TS + Hono)
2. **不实现 defer 列表中任何项**:哪怕"顺手就能加"也不加,**控制 scope creep 是 v0.2 sprint 最大成功条件**
3. **5 道闸不破**:typecheck / lint / test / build / e2e 全过(foundation 已搭好的 CI 矩阵)
4. **dogfood 即验证**:gate 用作者真实使用记录(查 sidecar 文件)判断,不引入埋点系统

## 开放风险(已认知)

1. **defer 列表过长可能事后证明 v0.2 太瘦** — 用户可能 dogfood 后觉得"光拍板没用,需要至少 N 个其他功能"。预案:v0.3 sprint 启动前重新评估,可能调整。
2. **22Q 探索的产品愿景与 v0.2 实际 scope 落差大** — 文档读者可能困惑"为什么不一步到位"。本决策文档负责消除这困惑。
3. **拍板的 UI 形态留待 design** — 本决策只锁功能集,UI(绿徽章 vs 上锁图标 vs 状态文字)在 v0.2 design 阶段拍板。
